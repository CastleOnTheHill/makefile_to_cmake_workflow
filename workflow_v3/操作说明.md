# workflow_v3 操作说明

workflow_v3 的核心变化是：Excel 看板是任务源、状态源、恢复源和人工反馈入口。
运行过程会尽量少生成其他文件，只保留分析 JSONL 和 OpenCode stdout/stderr 日志。

## 1. 安装依赖

```bash
python3 -m pip install --user -r workflow_v3/requirements.txt
```

## 2. 准备配置

```bash
cp workflow_v3/config.example.json workflow_v3/config.local.json
```

修改 `workflow_v3/config.local.json`：

- `project_root`：原工程根目录。
- `scan_subdir`：要转换的子目录。
- `board_path`：Excel 看板路径，默认 `workflow_v3/state/tasks.xlsx`。
- `state_dir`：运行日志和分析 JSONL 目录。
- `opencode_bin`：内部 opencode 路径。
- `model`：例如 `deepseek/deepseek-v4-pro`。
- `api_key_file`：API key 文件。
- `build_commands`：转换后用于验证的配置/编译命令列表。

v3 固定把 CMake 生成到 mk 或 Makefile 同级目录下的 `CMakeLists.txt`，不再配置
`cmake_output_dir`。

## 3. 发现任务并创建 Excel

```bash
workflow_v3/scripts/discover_mk_files.py workflow_v3/config.local.json
```

小规模试跑：

```bash
workflow_v3/scripts/discover_mk_files.py workflow_v3/config.local.json --limit 50
```

这一步会扫描 `Android.mk`、`*.mk`、`Makefile`，每个文件都进入 Excel。即使某个 mk
被其他 mk include，也不会跳过。

Excel 必含列：

- `原始mk/makefile路径`
- `转换后cmake文件路径`
- `是否完成分析`
- `分析是否成功`
- `是否完成转换`
- `转换是否成功`
- `人工意见`

你可以在 Excel 中增加其他列，脚本会保留。

## 4. 分析 Makefile/mk

```bash
workflow_v3/scripts/analyze_mk_files.py workflow_v3/config.local.json -j 3
```

常用参数：

- `--limit 100`：只跑 100 个待分析项，方便分批执行。
- `-j 3`：同时启动 3 个 opencode 分析任务。
- `--timeout 1800`：单个 opencode 超时秒数，超时会杀进程组并继续后续任务。
- `--force`：选中的任务即使之前分析成功也重新分析。
- `--mk-file path/to/package.mk`：只分析某个 Excel 中已有的文件，可重复传。
- `--file-list list.txt`：从文本列表读取要分析的文件。

分析成功后，Excel 会更新分析状态，并把目标 JSONL 写到 `state_dir/analysis/<任务ID>.jsonl`。
如果失败或超时，下次默认会重试。

## 5. 转换 CMake

```bash
workflow_v3/scripts/convert_targets.py workflow_v3/config.local.json -j 3
```

常用参数：

- `--limit 100`：只跑 100 个待转换项。
- `-j 3`：同时启动 3 个 opencode 转换任务。
- `--timeout 1800`：单个 opencode 超时秒数。
- `--force`：强制重新转换选中的项。
- `--only-commented`：只处理 Excel 中 `人工意见` 非空且未完成的行。
- `--mk-file path/to/package.mk`：只转换某个文件。

转换输出固定为原始 mk 或 Makefile 同级目录下的 `CMakeLists.txt`。
多个 mk 位于同一目录时，脚本会对同一个 `CMakeLists.txt` 串行加锁，避免并行写冲突。

## 6. 人工反馈恢复

人工审查生成的 `CMakeLists.txt` 后，如果发现问题：

1. 在 Excel 对应行的 `人工意见` 写入意见，例如 `条件 USE_SSL 没有转换成 if(USE_SSL)`。
2. 再运行：

```bash
workflow_v3/scripts/convert_targets.py workflow_v3/config.local.json --only-commented -j 3
```

脚本会把意见放进转换 prompt，强制重新生成这一行。转换成功后，`人工意见` 会变成：

```text
已完成：条件 USE_SSL 没有转换成 if(USE_SSL)
```

如果还不满意，把这一格改成新的意见，再运行转换即可。

## 7. 一键分批运行

```bash
workflow_v3/scripts/run_all.py workflow_v3/config.local.json -j 3 --limit 100 --timeout 1800
```

这会依次执行 discover、analyze、convert。大工程建议先用 `--limit` 试跑，确认 prompt
和生成风格后再扩大数量。

## 8. fake OpenCode 试跑

如果只想在真实工程里验证 workflow_v3 的流程、Excel 看板、并行调度、恢复逻辑和同级
`CMakeLists.txt` 写入，不想调用真实模型，可以使用 fake 命令：

```bash
workflow_v3/scripts/run_fake.py workflow_v3/config.local.json -j 8 --limit 100
```

这个命令会临时把 `opencode_bin` 替换成 `workflow_v3/scripts/fake_opencode.py`，
不需要修改你的 `config.local.json`。

fake 模式行为：

- discover 正常扫描真实工程并创建 Excel。
- analyze 为每个 mk/Makefile 生成一个占位 JSON target，不做真实分析。
- convert 在 mk/Makefile 同级写入最小 `CMakeLists.txt`。
- 生成的 `CMakeLists.txt` 不包含真实 target，只保留 workflow trace 注释，用于让状态判定为转换成功。
- Excel 会正常回写分析/转换状态。

只跑某一步：

```bash
workflow_v3/scripts/run_fake.py workflow_v3/config.local.json --stage discover --limit 100
workflow_v3/scripts/run_fake.py workflow_v3/config.local.json --stage analyze -j 8 --limit 100
workflow_v3/scripts/run_fake.py workflow_v3/config.local.json --stage convert -j 8 --limit 100
```

只测试某些文件：

```bash
workflow_v3/scripts/run_fake.py workflow_v3/config.local.json --stage analyze --mk-file path/to/package.mk --force-analyze
workflow_v3/scripts/run_fake.py workflow_v3/config.local.json --stage convert --mk-file path/to/package.mk --force-convert
```

## 9. 循环配置/编译并自动修复

配置中添加 `build_commands`，从上往下写多条命令：

```json
"build_commands": [
  {
    "name": "configure",
    "cwd": ".",
    "command": "cmake -S path/to/subproject -B out/build -G Ninja"
  },
  {
    "name": "build",
    "cwd": ".",
    "command": "cmake --build out/build -j 8"
  }
]
```

执行：

```bash
workflow_v3/scripts/build_repair_loop.py workflow_v3/config.local.json
```

行为：

- 按 `build_commands` 顺序执行，任意命令失败就停止本轮构建。
- 边执行边保存完整日志到 `state/logs/build.<attempt>.<command>.log`，内存中只保留
  最近一段输出用于错误摘要，适合长时间运行。
- 控制台实时打印当前命令输出，并明确显示何时交给 OpenCode 处理、何时返回。
- 长时间命令会周期性刷新 `build_repair_state.json` 心跳和日志文件。
- 提取错误摘要和失败签名，调用 `v3-build-fixer` 修复。
- `v3-build-fixer` 只能创建或修改 `CMakeLists.txt`，不能修改源码、头文件、
  Makefile、Android.mk 或 `*.mk`。
- 不再要求最小改动。如果一个失败暴露出共性转换问题，可以统一修改其他相关
  `CMakeLists.txt`，保持同类 target 写法一致。
- 修复前后只对 `build_repair_snapshot_roots` 下的 `CMakeLists.txt` 做 diff，并把
  每个改动文件的 diff 写入 `build_repair_log.md`。
- 修复后重新从第一条命令开始验证。
- 如果 OpenCode 超时，会按 `build_fix_opencode_retries` 重试。
- 如果同一个失败签名重复 `max_same_failure` 次，会停止并写
  `manual_required.md`，等待人工介入。
- 同一时间只允许一个 `build_repair_loop.py` 持有 `build_repair.lock`，避免多个进程
  同时改状态和日志。
- Ctrl+C 或 SIGTERM 会尽量杀掉当前构建/OpenCode 子进程，并把状态写成
  `interrupted`。重新执行同一命令即可继续，新的 attempt 编号会参考已有日志和状态，
  不会覆盖旧日志。`kill -9` 无法被捕获，但状态文件使用原子写，后续重跑也会按已有
  日志恢复编号。

常用参数：

- `--limit-attempts 2`：本次最多尝试 2 轮，适合小规模验证。
- `--reset-state`：清空构建修复状态，从头跑。

人工介入：

1. 查看 `workflow_v3/state/manual_required.md` 和 `build_repair_log.md`。
2. 手动修改 CMake 或相关文件。
3. 重新执行 `workflow_v3/scripts/build_repair_loop.py workflow_v3/config.local.json`。

经验文件：

- `build_manual_experience.md` 是人工维护的经验文件，脚本只读取，不压缩、不覆盖。
- 有效推进构建的修复会沉淀到 `build_experience.md`。
- `build_experience.md` 会按行数自动压缩，保持精简。
- `build_repair_loop.py` 会同时参考人工经验和自动经验；后续 `convert_targets.py`
  继续参考自动经验。

fake 验证构建修复流程：

```bash
workflow_v3/scripts/run_fake.py workflow_v3/config.local.json --stage build
```

fake 模式不会真实修复文件，只用于验证构建循环、日志、状态和人工交接路径。
