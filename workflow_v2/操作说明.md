# Workflow V2 操作说明

`workflow_v2/` 是面向复杂多产品 C/C++ 嵌入式项目的新工作流骨架。它按你的设想拆成三类 agent，并用外部脚本负责发现、派发、编译、修复和人工恢复。

## 1. 三个 Agent

Agent 文件在：

```text
.opencode/agent/v2-mk-analyzer.md
.opencode/agent/v2-cmake-converter.md
.opencode/agent/v2-build-fixer.md
```

`v2-mk-analyzer`

- 输入一个 Makefile/Android.mk/*.mk 文件。
- 必要时自动读取 include 文件。
- 输出 JSONL，每一行代表一个构建目标。
- 保留条件编译信息，例如 `ifeq/ifneq/ifdef/ifndef` 对 source、include、define、flags、deps 的影响。
- 如果文件只是 include 聚合，例如 `include $(LOCAL_PATH)/*/package.mk`，不会展开子目录
  `package.mk` 生成重复 target，而是输出一个 `target_type: "include_aggregator"` 记录。

`v2-cmake-converter`

- 输入一个 target JSON。
- 在配置的 CMake 输出目录生成或修改 CMake 文件。
- 只生成一个 `CMakeLists.txt`，不再拆分 `generated_targets.cmake`。
- 生成的 `CMakeLists.txt` 不定义 `project()`，总工程由外部根 `CMakeLists.txt` 定义。
- Makefile/Android.mk 中的开关会直接用 `if(XXX)` 判断，不在子目录 CMake 中定义
  `option(XXX ...)`，这些开关由外部根 CMake 工程统一处理。
- 条件编译必须真正实现：如果某个开关会增加源文件、宏、include、编译选项、链接库或
  链接选项，生成的 CMake 必须使用 `if(...) target_sources(...)`、
  `if(...) target_compile_definitions(...)` 等真实逻辑，不能只保留注释。
- 如果转换过程中没有找到开关变量定义，不需要处理；直接使用该变量即可。
- 源文件和路径通配必须展开或显式建模，不能直接写成
  `target_sources(lib PRIVATE src/*.cpp)`、`add_library(lib src/*.c)` 这类无效 CMake。
  CMake 的 target 命令不会自动展开 `*`、`?`、`[]`、`**`。
- 每个生成的 target 块都带追踪注释：

```cmake
# workflow_v2:target_id=<target_id> source_mk=<source_mk> module=<module>
```

- 对 `include_aggregator` 不生成库或可执行文件，只生成 `include(...)`、
  `add_subdirectory(...)` 或保守的聚合注释。
- 生成 `add_subdirectory()` 前必须确认对应子目录已经存在 `CMakeLists.txt`。

`v2-build-fixer`

- 输入一次构建失败日志、产品名、构建命令、失败签名和 CMake 输出目录。
- 只做最小修复。
- 不自己执行编译，编译由外部循环脚本负责。

## 2. 配置文件

先复制模板：

```bash
cp workflow_v2/config.example.json workflow_v2/config.local.json
```

重点修改：

```json
{
  "project_root": ".",
  "scan_subdir": "path/to/your/subdir",
  "cmake_output_layout": "centralized",
  "cmake_output_dir": "path/to/generated/cmake",
  "products": [
    {
      "name": "product_a",
      "build_command": "your configure/build command for product_a"
    },
    {
      "name": "product_b",
      "build_command": "your configure/build command for product_b"
    }
  ]
}
```

`scan_subdir` 是团队经常修改、准备迁移到 CMake 的子目录。

`products` 只用来表达一套代码需要多次配置和构建验证。这里的 `name` 和
`build_command` 不会作为 Makefile/CMake 条件传给分析 agent，也不会用于生成
`if(PRODUCT_NAME)` 或按产品名 gated 的 `add_subdirectory()`。

`cmake_output_layout` 支持两种模式：

```json
"cmake_output_layout": "centralized"
```

集中输出到：

```text
<cmake_output_dir>/CMakeLists.txt
```

也可以使用：

```json
"cmake_output_layout": "beside_mk"
```

此时每个 target 会根据 `source_mk` 定位到对应 `.mk/Makefile` 所在目录，并在同目录生成：

```text
<mk 所在目录>/CMakeLists.txt
```

真实项目里，如果你希望迁移结果直接落在原始业务子目录中，使用 `beside_mk` 更合适。

## 3. 执行步骤

所有子命令都支持限制处理数量，便于先用小样本验证流程：

```bash
--limit 5
```

`analyze_mk_files.py`、`convert_targets.py` 和总入口额外支持并行 OpenCode 任务：

```bash
-j 4
```

分析和转换阶段还支持单个 OpenCode 调用超时：

```bash
--timeout 1800
```

如果没有传 `--timeout`，脚本会读取配置中的
`analysis_opencode_timeout_seconds`、`conversion_opencode_timeout_seconds`，
再 fallback 到 `opencode_timeout_seconds`。超时后会终止 OpenCode 进程组，记录状态，
然后继续处理下一项，避免并行模式中某个 OpenCode 无响应导致整体卡住。

分析和转换默认开启恢复执行：

- 已成功的分析结果会从已有 `.v2-mk-analyzer.out` 复用，并重新汇总到 `targets.jsonl`。
- 已成功的转换结果会根据 `conversion_status.jsonl` 或 `CMakeLists.txt` 中的
  `workflow_v2:target_id=...` 追踪注释跳过。
- 缺失、失败、超时的项会在下一次执行时重试一次。
- 如需强制全部重跑，使用 `--no-resume`。

并行分析会让每个 mk 文件独立写自己的 prompt/stdout/stderr 日志，最后按原始 mk 文件顺序
合并 `targets.jsonl`。并行转换会按 CMake 输出目录加锁：不同目录可以并行，同一个
`CMakeLists.txt` 会串行处理，避免多个 OpenCode 同时修改同一个文件。

分析前脚本会先预扫描 `include`、`-include`、`sinclude`：

- 如果 package.mk A include 了 package.mk B，且 A 不是纯 include 聚合文件，则认为 B
  可能是 A 这个产物的一部分。B 会作为 A 的 include 候选进入 prompt；如果 B 也在待分析
  列表里，会写入 `skipped_mk_files.jsonl`，不再作为独立主文件重复分析。
- 如果 include 使用变量或通配符，例如
  `-include $(project)/$(project/sub_type)/xxxx/package.mk`，脚本默认只在第一步
  `discover_mk_files.py` 已经发现的 mk/Makefile 列表中按固定后缀匹配候选，不会再递归扫描
  文件系统。默认最多收集 200 个候选，可以通过 `include_candidate_limit` 调整。
- 如果某个文件只是纯 include 聚合文件，例如 `include $(LOCAL_PATH)/*/package.mk`，
  不会把子目录里的 package.mk 标记为 covered，仍保留子目录文件后续独立分析。

如果 Ctrl+C 看到最后栈在 `enrich_and_filter_mk_rows()`，说明还没进入 OpenCode，
而是卡在本地 include 预扫描。可以用下面方式定位或绕过：

```bash
workflow_v2/scripts/analyze_mk_files.py workflow_v2/config.local.json -j 3 --no-include-prescan
```

或者在配置中降低 include 传递深度：

```json
"include_prescan_enabled": true,
"include_transitive_depth": 1
```

`analyze_mk_files.py` 不再递归搜索文件系统。它只使用
`discover_mk_files.py` 写出的 `state/mk_files.jsonl` 作为 include 候选集合。
如果候选缺失，先重新执行 discover 或调整 `mk_file_patterns` / `ignore_dirs`，
不要让 analyze 阶段扩大搜索范围。

### 3.1 发现 mk 文件

```bash
workflow_v2/scripts/discover_mk_files.py workflow_v2/config.local.json
workflow_v2/scripts/discover_mk_files.py workflow_v2/config.local.json --limit 10
```

输出：

```text
workflow_v2/state/mk_files.jsonl
workflow_v2/state/status.md
```

`mk_files.jsonl` 是待分析的 Makefile/Android.mk/*.mk 文件列表。

### 3.2 分析 mk 文件生成 target 任务

```bash
workflow_v2/scripts/analyze_mk_files.py workflow_v2/config.local.json
workflow_v2/scripts/analyze_mk_files.py workflow_v2/config.local.json --limit 10
workflow_v2/scripts/analyze_mk_files.py workflow_v2/config.local.json --limit 10 -j 4 --timeout 1800
```

也可以不依赖 `discover_mk_files.py` 的结果，手工指定一组典型文件：

```bash
workflow_v2/scripts/analyze_mk_files.py workflow_v2/config.local.json \
  --mk-file path/to/Android.mk \
  --mk-file path/to/module.mk \
  -j 4
```

如果文件较多，可以写成文本列表：

```text
# typical_mk_files.txt
path/to/Android.mk
path/to/module.mk
path/to/Makefile
```

然后执行：

```bash
workflow_v2/scripts/analyze_mk_files.py workflow_v2/config.local.json \
  --file-list typical_mk_files.txt \
  -j 4
```

`--mk-file` 和列表文件中的路径可以是绝对路径，也可以是相对 `project_root` 的路径。
`--file-list` 也可以写成 `--mk-list`。列表中空行和 `#` 开头的行会被忽略。

每个 mk 文件会调用一次：

```bash
opencode run --agent v2-mk-analyzer ...
```

输出：

```text
workflow_v2/state/targets.jsonl
workflow_v2/state/analyze_inputs.jsonl
workflow_v2/state/skipped_mk_files.jsonl
workflow_v2/state/analysis_status.jsonl
workflow_v2/state/prompts/*.v2-mk-analyzer.md
workflow_v2/state/opencode_results/*.v2-mk-analyzer.out
workflow_v2/state/logs/*.v2-mk-analyzer.err
```

`analyze_inputs.jsonl` 记录本次实际分析的输入文件，包含手工指定的文件列表。
`skipped_mk_files.jsonl` 记录因为已被其他主 mk include 覆盖而跳过的文件。

`targets.jsonl` 是后续 CMake 转换的核心输入。

### 3.3 分发 target 给 CMake 转换 agent

```bash
workflow_v2/scripts/convert_targets.py workflow_v2/config.local.json
workflow_v2/scripts/convert_targets.py workflow_v2/config.local.json --limit 20 -j 4 --timeout 1800
```

每个 target JSON 会调用一次：

```bash
opencode run --agent v2-cmake-converter ...
```

输出到配置项：

```json
"cmake_output_dir": "..."
```

默认会保证存在：

```text
<cmake_output_dir>/CMakeLists.txt
```

转换尝试状态写入：

```text
workflow_v2/state/conversion_status.jsonl
```

如果配置了：

```json
"cmake_output_layout": "beside_mk"
```

则上述文件会生成到每个 target 对应的 `.mk/Makefile` 同目录，而不是 `cmake_output_dir`。

### 3.4 编译循环和自动修复

```bash
workflow_v2/scripts/build_repair_loop.py workflow_v2/config.local.json
workflow_v2/scripts/build_repair_loop.py workflow_v2/config.local.json --limit 1
```

这个脚本按 `products` 顺序循环：

```text
执行 product build_command
-> 成功则记录 done
-> 失败则截取错误日志
-> 计算失败签名
-> 调 v2-build-fixer 修复
-> 再次执行 build_command
```

构建状态写入：

```text
workflow_v2/state/build_state.jsonl
workflow_v2/state/logs/build.<product>.attempt-<n>.log
```

脚本会打印当前处理对象和简单进度条，例如：

```text
[  3/12 ] [#######---------------------] analyze path/to/Android.mk
[  5/20 ] [#######---------------------] convert target_x -> path/to/module
```

## 4. 构建停滞和人工介入

配置项：

```json
"max_fix_attempts_per_product": 8,
"max_same_failure": 3
```

含义：

- 单个产品最多自动修复 8 次。
- 如果同一个失败签名连续出现 3 次，认为进度没有推进。

停滞后脚本会停止，并写入：

```text
workflow_v2/state/manual_required.md
```

人工处理流程：

1. 查看 handoff：

```bash
cat workflow_v2/state/manual_required.md
```

2. 查看最后一次构建日志：

```bash
ls workflow_v2/state/logs
```

3. 人工修改生成的 CMake 或补充必要输入。

4. 标记已人工处理：

```bash
workflow_v2/scripts/mark_manual_fixed.py workflow_v2/config.local.json <product-or-task-id>
```

5. 继续编译修复循环：

```bash
workflow_v2/scripts/build_repair_loop.py workflow_v2/config.local.json
```

## 5. 一键串联

如果配置已经准备好，可以直接：

```bash
workflow_v2/scripts/run_all.py workflow_v2/config.local.json
workflow_v2/scripts/run_all.py workflow_v2/config.local.json --limit 5 -j 3
```

这会依次执行：

```text
discover_mk_files.py
analyze_mk_files.py
convert_targets.py
build_repair_loop.py
```

## 6. 真实项目接入建议

建议先对一个产品、一个较小子目录跑通：

```json
"products": [
  {
    "name": "product_a_debug",
    "build_command": "你的 product_a debug 构建命令"
  }
]
```

跑通后再增加产品：

```json
"products": [
  {"name": "product_a_debug", "build_command": "..."},
  {"name": "product_a_release", "build_command": "..."},
  {"name": "product_b_debug", "build_command": "..."}
]
```

对于复杂条件编译，重点检查：

```text
workflow_v2/state/targets.jsonl
```

确认 `conditions` 字段是否完整表达了产品差异，再进入 CMake 转换。
