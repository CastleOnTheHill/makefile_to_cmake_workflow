# Android.mk / Makefile 子工程转 CMake 工作流操作说明

本文档说明如何使用当前 workspace 中的 demo 工作流，将 Makefile/Android.mk 子工程转换为可单独编译的 CMake 子工程，并通过 OpenCode + DeepSeek 辅助分析、修复和验证。

## 1. 当前环境状态

当前目录已经完成以下准备：

- OpenCode 已安装到本地目录：`.tools/node_modules/.bin/opencode`
- OpenCode 版本：`1.15.12`
- DeepSeek API key 从 `mykey.txt` 读取，只在运行时注入环境变量，不写入日志
- cJSON 和 libcurl demo 源码已下载到 `demo/`
- cJSON 和 libcurl 的原始构建、CMake 转换构建、产物验证均已跑通

关键验证报告：

- `workflow/verify_cjson.md`
- `workflow/verify_libcurl.md`

## 2. 一键运行 demo

只跑 cJSON：

```bash
scripts/run_demo.sh cjson
```

只跑 libcurl：

```bash
scripts/run_demo.sh libcurl
```

两个 demo 都跑：

```bash
scripts/run_demo.sh all
```

运行后重点查看：

```bash
cat workflow/status.md
cat workflow/verify_cjson.md
cat workflow/verify_libcurl.md
```

## 4. 工作流阶段

整个流程分为 6 步：

1. 安装和检查 OpenCode

```bash
scripts/bootstrap_opencode.sh
```

脚本会优先使用 npm 官方源；如果失败，会 fallback 到 `https://registry.npmmirror.com`。安装目标是当前 workspace 的 `.tools/`，不是系统目录。

2. 下载 demo 源码

```bash
scripts/prepare_demo_sources.sh cjson
scripts/prepare_demo_sources.sh libcurl
scripts/prepare_demo_sources.sh all
```

默认版本：

- cJSON：`v1.7.19`
- libcurl：`curl-8_15_0`

3. 捕获原始构建

```bash
scripts/capture_original_build.sh cjson
scripts/capture_original_build.sh libcurl
```

该步骤会保存原始 Makefile/autotools 构建日志和产物列表：

```text
demo/<project>/original/build.log
demo/<project>/original/artifacts.txt
```

4. 拆分转换任务

```bash
scripts/plan_tasks.py cjson
scripts/plan_tasks.py libcurl
scripts/plan_tasks.py all
```

输出：

```text
workflow/tasks.jsonl
workflow/status.md
```

每一行 JSON 是一个可独立恢复的转换任务。

5. 调用 OpenCode 分析单个任务

```bash
scripts/run_opencode_task.sh cjson-core mk-analyzer
scripts/run_opencode_task.sh libcurl-library mk-analyzer
```

输出：

```text
workflow/opencode/<task-id>.<agent>.prompt.md
workflow/opencode/<task-id>.<agent>.result.md
workflow/logs/<task-id>.<agent>.stderr.log
```

如果 OpenCode 没有输出最终 Markdown，脚本也会把工具读取 trace 摘要写入 result 文件，方便人工接手。

6. 生成 CMake、构建和验证

```bash
scripts/generate_cmake_from_task.py cjson-core
scripts/build_step.sh cjson
scripts/verify_outputs.py cjson
```

libcurl：

```bash
scripts/generate_cmake_from_task.py libcurl-library
scripts/build_step.sh libcurl
scripts/verify_outputs.py libcurl
```

## 5. 中断和恢复

如果流程中断，直接运行：

```bash
scripts/resume_workflow.sh
```

恢复逻辑：

- 读取 `workflow/tasks.jsonl`
- 逐个任务重新运行 OpenCode 分析
- 重新生成 CMake
- 重新构建
- 重新验证
- 如果失败，会记录到 `workflow/manual_required.md`

人工修复后，再次运行：

```bash
scripts/resume_workflow.sh
```

## 6. 当前 demo 验证结果

cJSON 验证摘要：

```text
Original artifact count: 8
Converted artifact count: 7
Converted compile command count: 5
Expected converted artifacts are present.
Artifact basename overlap: libcjson.a, libcjson_utils.a
```

libcurl 验证摘要：

```text
Original artifact count: 7
Converted artifact count: 15
Converted compile command count: 266
Expected converted artifacts are present.
Artifact basename overlap: curl, libcurl.a
```

差异说明：

- cJSON 原始 Makefile 会生成 `.so.1`、`.so.1.7.19` 等符号链接和版本库文件；当前 demo 验证重点是核心静态库、动态库、utils 库和测试程序是否存在。
- libcurl CMake 构建会生成更多中间工具或辅助产物；当前验证重点是 `libcurl.a` 和 `curl` 是否存在，以及是否生成 `compile_commands.json`。

## 7. 接入真实 Android.mk 大项目

真实项目接入时建议按下面顺序做。

1. 准备输入

需要提供：

- 原始总入口 bash 构建命令
- 目标产品参数
- 目标子目录路径
- 原始项目生成的 `compile_commands.json`
- 初始 hello world CMake 交叉编译工程
- 外部依赖头文件路径
- 外部依赖库产物路径

2. 捕获原始构建事实

对每个产品配置执行原始构建，保存：

```text
original/<product>/build.log
original/<product>/compile_commands.json
original/<product>/artifacts.txt
original/<product>/link_commands.txt
```

重点提取：

- 子目录内源文件
- `LOCAL_MODULE`
- `LOCAL_SRC_FILES`
- `LOCAL_C_INCLUDES`
- `LOCAL_EXPORT_C_INCLUDE_DIRS`
- `LOCAL_CFLAGS`
- `LOCAL_CPPFLAGS`
- `LOCAL_SHARED_LIBRARIES`
- `LOCAL_STATIC_LIBRARIES`
- 产品相关开关

3. 拆任务

任务拆分粒度建议：

- 一个 Android.mk module 一个任务
- 一个 library/executable/gtest 目标一个任务
- 复杂 module 再按 source group 或 feature flag 拆分

任务文件仍使用 `workflow/tasks.jsonl`，每个任务必须包含：

- module 名称
- 产物类型：shared/static/executable/gtest
- 源文件列表
- include 路径
- define 列表
- compile options
- link libraries
- link options
- 依赖的外部预构建产物
- 对应产品配置

4. 运行 OpenCode

每个任务只喂必要上下文：

- 当前 Android.mk 片段
- 当前 module 的 compile_commands 子集
- 当前 module 的 link log
- 相关头文件摘要
- 当前 CMake 片段
- 上一次失败日志

不要一次把整个大项目交给模型。

5. 单步编译试错

推荐循环：

```text
生成/修改一个 target
-> cmake configure
-> cmake --build <target>
-> 失败则截取最小错误日志给 build-fixer
-> 成功后进入下一个 target
```

连续失败超过阈值时，写入：

```text
workflow/manual_required.md
```

人工修复后继续 `resume_workflow.sh`。

6. 验证转换正确性

至少比较：

- 目标产物名称
- 目标产物类型
- 源文件集合
- include dirs
- compile definitions
- compile options
- link libraries
- link options
- `compile_commands.json`
- gtest 可执行文件是否能构建和运行

## 8. 常见问题

OpenCode 没有输出最终回答：

- 看 `workflow/logs/*.stderr.log`
- 当前脚本会把 trace 摘要写入 `workflow/opencode/*.result.md`
- 不阻塞确定性 CMake 生成和验证

npm 官方源失败：

- `bootstrap_opencode.sh` 会自动 fallback 到 npmmirror

libcurl 原始 configure 找不到依赖：

- demo 已显式关闭 `ssl/zlib/libpsl/brotli/zstd` 等可选依赖
- 真实项目应根据原始产品配置锁定所有 feature 开关

需要 sudo：

- 当前 demo 没有使用 sudo
- 如果真实环境需要安装系统依赖，再读取 `pswd.txt` 并通过 `sudo -S` 执行
